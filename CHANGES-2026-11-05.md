## Dashboard crash düzeltmesi (Koin scope)

**Belirti:** Login başarılı, ancak Dashboard ekranında uygulama çöküyordu.

**Logcat:**
```
org.koin.core.error.ScopeAlreadyCreatedException: Scope with id 'DASHBOARD_SCOPE' is already created
  at DashboardMainModule$createDashboardModule$1$1.invoke(DashboardMainModule.kt:22)
→ InstanceCreationException: Could not create instance for [Factory:'DashboardMainViewModel']
→ FATAL EXCEPTION: main
```

**Kök neden:** Scope oluşturma `viewModel { }` factory'sinin *içinde* yapılıyor.
Factory her ViewModel oluşturulduğunda yeniden çalıştığı için `createScope` ikinci kez
çağrılıyor. `org.koin` → `io.insert-koin` 2.1.6 geçişiyle birlikte bu durum artık
sessizce geçilmiyor, `ScopeAlreadyCreatedException` fırlatılıyor.

**Düzeltme:** `getKoin().createScope(...)` → `getKoin().getOrCreateScope(...)`

| Dosya | Satır |
|---|---|
| `feature_dashboard/.../main/di/DashboardMainModule.kt` | 22 |
| `feature_payment/.../payment_list/di/PaymentListModule.kt` | 14 |
| `feature_appliance/.../appliance_list/di/ApplianceListModule.kt` | 14 |

## Dashboard'un balance grafiğine bağımlılığının kaldırılması

**Belirti:** Crash giderildikten sonra Dashboard kartları shimmer (iskelet)
halinde kalıyordu.

**Kök neden (backend):** `GET /api/app/agents/dashboard/graph` yanıt vermiyor.

```
  {"company_id":22,"company_name":"Volt-Terra"}
nginx: "GET /api/app/agents/dashboard/graph HTTP/1.1" 500 941293
```

`DashboardMainViewModel` üç isteği `Singles.zip` ile birleştirdiği için bu tek
hata tüm ekranı Loading/Error'da bırakıyordu.

**Not:** Bu endpoint period/tarih parametresi kabul etmiyor —
`AgentDashboardBalanceHistoryController::show()` `Request`'i hiç okumuyor, aralık
tamamen sunucuda belirleniyor (`getLastReceiptDate()`, yoksa agent'ın `created_at`'i).
Dolayısıyla app'ten gönderilecek bir `period` parametresiyle daraltmak mümkün değil.

- `.timeout(15, SECONDS)` — 30 sn'lik OkHttp timeout'unu beklemek yerine erken vazgeçer.
- `.onErrorReturn { ... }` — hata/timeout durumunda grafiği boş olarak yayınlar
  (`DashboardGraphBalanceUiState.Success(arrayListOf(), emptyList())`).

Böylece Dashboard özet kartları ve revenue grafiği normal şekilde yüklenir; balance
grafiği ise MPAndroidChart'ın kendi "There is no data to present yet" mesajını gösterir.

### Bildirime tıklayınca boş ekran — PendingIntent extra'ları

**Belirti:** Bildirim geliyordu, ama tıklayınca Success ekranında NAME SURNAME,
METER ve TOKEN boş, AMOUNT `0.00` görünüyordu.

**Kök neden (app):** `MerchantFirebaseMessagingService.displayNotification()`

```kotlin
PendingIntent.getActivity(this, 0, intent, PendingIntent.FLAG_ONE_SHOT)
```

Intent extra'ları `Intent.filterEquals`'a dahil değildir. Request code her bildirim
için sabit `0` olduğundan ve `FLAG_UPDATE_CURRENT` verilmediğinden, Android mevcut
PendingIntent'i **ilk oluşturulduğu andaki extra'larla** geri veriyordu. Yani
bildirime tıklandığında ekrana *başka bir* ödemenin payload'ı (ya da hiç payload)
geliyordu; `Gson` null döndürünce tüm alanlar boş, `amount` da
`?: BigDecimal.ZERO` ile `0.00` oluyordu.

**Düzeltme:** request code olarak bildirim id'si kullanılıyor ve
`FLAG_UPDATE_CURRENT` ekleniyor (API 23+ için `FLAG_IMMUTABLE` ile birlikte —
targetSdk 34'e çıkılırsa Android 12+ zaten bunu zorunlu kılıyor).

*Not: `NotificationHandler` düz `Gson()` kullanıyor, ağ katmanı ise
`setDateFormat(DATE_FORMAT_FULL)` ile kuruluyor. Bu bir sorun değil — Gson'ın tarih
adaptörü yapılandırılmış formatı deneyip ISO8601'e düşüyor, Laravel'in
`...000000Z` formatı böyle çözülüyor.*

tıklandı. Ekran: Ronald Sejjuko (CM95047106ND8A) / 47001750364 / 750.00 NGN /

## Ticket detayı açılmıyordu — Trello'dan kalma `ticket_id`

**Belirti:** Ticket app'ten başarıyla oluşturuluyor, listede görünüyor; ama detaya
tıklayınca "An error occurred. Please try again later".

**Kök neden (app):** Liste ve detay modelleri `ticket_id` alanını okuyordu:

```kotlin
data class Ticket(@SerializedName("ticket_id") val ticketId: String, ...)
TicketListUiState.TicketTapped(ticket.ticketId)
```

`ticket_id` Trello döneminden kalma bir sütun — Trello kart id'sini tutuyordu.
Ticketlar artık yerel oluşturulduğu için **boş string** kalıyor:

```json
{ "id": 1, "ticket_id": "", "title": "Ticket", "content": "aaaa", ... }
```

Boş id ile detay URL'i `GET /api/app/agents/ticket/` oluyordu. Bu istek index
rotasına düşüp **200 ile sayfalı liste** döndürüyor, `TicketDetailResponse` olarak
parse edilemeyince hata diyalogu çıkıyordu. Yani ne 404 ne 500 — sessizce yanlış
uca gidiyordu, bu yüzden teşhisi zordu.

**Ayrıca detay modeli iki alanda daha uyumsuzdu:**

| App bekliyordu | Gerçek yanıt |
|---|---|
| `ticket_id` (String) | `id` (sayı) |
| `ticket.desc` (Trello kartı) | `content` (üst seviye sütun) |

Yani detaya ulaşılabilse bile ID ve açıklama boş görünecekti.

**Düzeltme** (`feature_ticket`):

| Dosya | Değişiklik |

## Appliance satışı — stok modelinden katalog + taksit modeline

**Belirti:** App'te "New Appliance" ekranı "You do not have any appliance to sell yet!"
diyordu; satış akışı tamamen kullanılamaz durumdaydı.

### MPM'deki yapı (analiz)

- **Katalog:** `assets` (name, asset_type_id, price) + `asset_types`
  (1 Solar Home System, 2 E-Bike, 3 Electronics)
- **Satış:** `asset_people` — asset_id, person_id, total_cost, rate_count,
  down_payment, first_payment_date, device_serial, **creator (morph)**
- **Taksit planı:** `asset_rates` — asset_person_id, rate_cost, remaining, due_date

**Web (admin):** `POST /api/assets/person/{asset}/people/{person}` tek transaction'da
satış satırını, fiyat sapma log'unu, taksit planını, cihaz bağlamayı ve peşinat için
cash transaction + `payment.successful` eventini üretiyor.

**Plan matematiği (`ApplianceRateService::create`):** peşinat varsa bugün tarihli,
kalanı 0 olan bir satır; ardından `rate_count` adet `floor(kalan/rate_count)`,
sonuncusu yuvarlama farkını yutar; vadeler `+1 ay/hafta`.

**İki sekme aynı payload'ı üretiyor;** fark yalnızca taksit sayısının nereden geldiği:
*count based* kullanıcı sayıyı girer, *cost based* tutarı girer →
`rate = floor((cost - downPayment) / floor(rateCost))`.

**Agent (eski):** `POST /api/app/agents/appliances` sadece `person_id` +
`agent_assigned_appliance_id` alıp `agent_sold_appliances`'a yazıyordu — fiyat yok,
taksit yok. `agent_assigned_appliances` tablosu boş olduğu için app'in listesi de boştu.

**Asıl çelişki:** agent'ın *satılanlar listesi* zaten `asset_people`'dan creator=Agent
okuyordu. Backend yarı göçmüştü: okuma yeni yapıda, yazma eskide.

### Peşinat artık gerçek bir ödeme + SHS/E-Bike cihaz seçimi

**Sorun:** Agent satışında peşinat yalnızca `asset_people.down_payment` alanında bir
sayıydı; ödeme kaydı oluşmuyordu. Web bunu `cash_transactions` üzerinden yapıyor ama
o tablonun `user_id` kolonu `users`'a bakıyor — **agent bir user değil** (kendi auth'u
olan ayrı tablo, `users` ile bağı yok). Agent id'si oraya yazılsa `CashTransaction::user()`
üzerinden raporlarda alakasız bir kullanıcıya atfedilirdi.

**Çözüm — polymorphic creator** (`asset_people.creator` ile aynı desen):

- Migration `2026_11_05_180000_add_creator_to_cash_transactions_table.php`:
  `creator_type` + `creator_id` eklendi (birlikte indexli), mevcut satırlar
  `creator_type='admin'` + `creator_id=user_id` ile backfill edildi, `user_id` nullable
  yapıldı. *Dikkat: `User::RELATION_NAME` bu projede `'user'` değil **`'admin'`**.*
- `CashTransactionService`: mevcut üç çağıran hiç değişmedi. `createCashTransaction()`
  eskisi gibi `user_id` yazıyor (legacy ilişki çalışsın) ve creator'ı `admin` işaretliyor.
  Agent için ayrı yol: `createCashTransactionForAgent()` — `user_id` boş, creator agent.
- Agent satışı peşinat > 0 ise işlemi oluşturup `payment.successful` eventini peşinat
  taksiti üzerinden tetikliyor.

**Cihaz seçimi** (`f232bef5`): `GET /api/app/agents/appliances/{assetId}/devices` →
`person_id` boş **ve** alttaki kaydı (`solar_home_systems`/`e_bikes`) o appliance'a ait
cihazlar. App'te appliance seçilince liste çekiliyor; doluysa **Device** seçici görünüp
zorunlu oluyor, boşsa hiç gösterilmiyor. Seçilen seri `device_serial` olarak gidiyor,
backend cihazı müşteriye bağlıyor. Layout'ta `Barrier` ile dizilim korunuyor.
